# 07. 연속 배송 pitch-hold PPO v4 재학습 결과

## 최종 판정

`arm_delivery_pitch_hold_v4`는 기존 PICK 전용 `arm_grasp_pitch_hold_v3`에서 이어 학습한 PICK/PLACE 겸용 정책이다. 일반 전체 타워 조건에서 `PICK → 파지 상태 Stay → 운송 대기 → PLACE → 빈 팔 Stay` 100회를 모두 완료했고 충돌은 없었다. 가장 강한 Sim2Real 연속 배송에서는 98/100 성공, 충돌 2/100을 기록해 시뮬레이션 배포 후보 기준 90%를 통과했다.

이 결과는 실제 로봇 자동 배송 승인이 아니다. 베이스 주행은 외부 이동 제어기가 담당하며 실제 로봇 런타임에 PLACE 상태 머신과 도착 handoff를 연결한 뒤 저속 안전 검증을 별도로 수행해야 한다.

## 변경된 임무 계약

기존 환경의 PICK과 PLACE 독립 episode에 `delivery` episode를 추가했다. 관측 33차원, action 4차원, 네 phase one-hot은 바꾸지 않아 기존 Python/C++ actor 인터페이스를 유지했다.

```text
PICK_REACH
  → object attached
PICK_TO_STAY
  → Stay 안정 8 step
  → transport hold 25/50/75 step
PLACE_REACH
  → 출발점과 분리된 목표로 재전개
  → release gate 4 step + open settle 12 step
PLACE_TO_STAY
  → placement error <= 15 mm
  → 빈 팔 Stay 안정 8 step
  → episode success
```

MuJoCo 모델은 고정 베이스이므로 transport hold 이후의 전환은 외부 베이스가 배송 위치에 도착한 handoff를 모사한다. 팔은 이 구간에서 물체를 쥔 실제 Stay를 유지한다.

## 환경과 학습 코드 변경

- `delivery_episode_probability`로 연속 배송 episode를 선택한다.
- 출발 물체 위치와 배치 목표 사이 XY 거리를 일반 조건에서 최소 15 mm로 분리한다.
- PICK 성공만으로 episode를 끝내지 않고 PLACE 및 빈 팔 Stay까지 완료해야 성공한다.
- PLACE 전환 시 PICK close gate를 초기화해 reference action이 정지하는 회귀를 막았다.
- 평가 보고서에 delivery PICK 완료율, PLACE 시작률, 출발/도착 위치 버킷을 추가했다.
- 최고 체크포인트 승격 뒤 PPO counter가 과거 평가 시점으로 되돌아가던 문제를 수정했다.
- metadata가 `[PICK, PLACE]`, `delivery_sequence_trained: true`, 단계별 transport hold를 기록한다.

## 학습

| 항목 | 값 |
|---|---|
| 시작 체크포인트 | `arm_grasp_pitch_hold_v3/arm_grasp_latest.zip` |
| 최종 정책 | `arm_delivery_pitch_hold_v4/arm_grasp_latest.zip` |
| 장치 | NVIDIA RTX 4050 Laptop GPU, CUDA |
| PPO 환경 수 | 8 |
| 네트워크 | MLP 256-256, tanh |
| 시작 counter | 21,024 |
| 최종 counter | 627,232 |
| action | 기준 제어 + PPO 잔차 10% |
| pitch hold | `joint2 + joint3 + joint4 = 0`, 최대 0.028 rad/step |

학습 stage는 다음 순서로 진행했다.

1. `place_center`, 50,000 요청 step
2. `place_return_center`, 40,000 요청 step
3. `place_full_tower`, 80,000 요청 step
4. `pick_place_mixed`, 100,000 요청 step
5. `delivery_center`, 60,000 요청 step
6. `delivery_full_tower`, 100,000 요청 step
7. `delivery_sim2real_robust`, 160,000 요청 step

PPO rollout 단위가 4,096 transition이므로 실제 최종 counter는 각 단계 요청량을 rollout 경계까지 올림한 627,232다. 각 stage는 독립 평가의 평균 보상이 가장 높은 체크포인트를 다음 stage로 승격했다.

## 독립 100회 평가

모든 평가는 학습 callback과 분리해 seed `20260802`, deterministic action으로 실행했다.

| 조건 | 성공 | 충돌 | 최종 파지 | 최종 release | 평균 step |
|---|---:|---:|---:|---:|---:|
| `full_tower` | 100/100 | 0/100 | 100% | 0% | 211.17 |
| `place_full_tower` | 100/100 | 0/100 | 0% | 100% | 219.42 |
| `pick_place_mixed` | 100/100 | 0/100 | 49% | 51% | 248.93 |
| `delivery_full_tower` | 100/100 | 0/100 | 0% | 100% | 613.61 |
| `delivery_sim2real_robust` | 98/100 | 2/100 | 1% | 99% | 715.47 |

`delivery_full_tower`는 PICK 완료율 100%, PLACE 시작률 100%, release율 100%다. Sim2Real은 PICK 완료율과 PLACE 시작률이 각각 99%였으며 실패 2건은 충돌 종료였다. 일반 조건의 출발·배치 목표 9개 위치 버킷에서는 모두 성공했다.

## MuJoCo 뷰어 확인

고정 seed `0`, `delivery_full_tower`를 GUI로 반복 재생했다. 확인한 네 episode가 모두 다음 로그로 끝났다.

```text
success=True
grasped=False
released=True
delivery_pick=True
delivery_place=True
collision=False
steps=613
```

뷰어에서 Stay 출발, 물체 bearing에 따른 joint1 회전, level pitch 접근, 파지, 물체를 든 Stay, 목표 재접근, release, 빈 팔 Stay를 확인했다.

```bash
cd /home/ktj/omx_train_ws
uv run --frozen python scripts/view_grasp_policy.py \
  --policy policies/latest/arm_delivery_pitch_hold_v4/arm_grasp_latest.zip \
  --stage delivery_full_tower \
  --episode-seed 0
```

## 남은 실제 로봇 작업

1. Python/C++ 런타임의 PICK 전용 거부 조건을 새 manifest 기반 `[PICK, PLACE]` 계약으로 변경한다.
2. PICK 완료 뒤 베이스 이동 동안 Stay+closed gripper를 유지한다.
3. 배송 위치 도착 및 정지 gate가 성립한 뒤 새 ArUco 목표로 PLACE를 시작한다.
4. 새 SB3 정책을 C++ actor binary로 내보내고 Python/C++ 출력 parity를 다시 검증한다.
5. 중앙·저속·단발 시험부터 진행하며 Sim2Real 충돌 2건에 해당하는 경계 위치를 초기 제한한다.
