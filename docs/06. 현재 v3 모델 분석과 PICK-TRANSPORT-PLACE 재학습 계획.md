# 06. 현재 v3 모델 분석과 PICK-TRANSPORT-PLACE 재학습 계획

## 결론

현재 실제 로봇 배포 모델 `arm_grasp_pitch_hold_v3`는 **PICK 전용 배포 계약**이다. 환경 코드에는 PLACE 기준 제어와 보상이 있지만, 해당 정책 체크포인트는 PLACE curriculum을 이수하지 않았고 전체 배송을 한 에피소드로 검증하지도 않았다. 최종 목표인 `물체 파지 → Stay에서 파지 유지 → 베이스 이동 완료 → 목표 위치 배치 → 빈 팔 Stay 복귀`를 현재 artifact가 보증한다고 볼 수 없다.

다만 PLACE 코드 자체가 없는 것은 아니다. 현재 정책을 `place_full_tower`에 강제로 넣은 진단 20회와 `pick_place_mixed` 20회는 모두 성공했다. 이는 PPO가 PLACE를 학습했다는 증거가 아니라, 정책 출력의 10% 잔차보다 충돌 회피 기준 제어기가 강하고 0 잔차 기준 경로도 PLACE를 완료하도록 설계됐기 때문이다.

| 공식 평가 종료 상태 | grasped 100%, released 0% |

### 33차원 관측

- 팔 관절 위치 4, 속도 4
- 그리퍼 위치·속도 2
- EEF 위치 3, 목표 위치 3, 상대 위치 3
- 목표 bearing sin/cos 2, 목표 yaw sin/cos 2
- EEF pitch 오차 1, 파지 상태 1
- 4단계 phase one-hot 4
- 이전 PPO action 4

### 4차원 action

PPO는 `joint1`~`joint4`의 절대 목표를 직접 출력하지 않는다.

```text
control = clip(reference + 0.10 * ppo_action, -1, 1)
filtered = EMA(control, coefficient=0.18)
joint_target += filtered * 0.014 rad
```

PICK/PLACE 접근 중에는 `joint4 = target_pitch - joint2 - joint3` 결합을 최대 `0.028 rad/step`으로 적용한다. 따라서 물체 bearing에 따른 joint1 회전과 EEF 카메라 pitch 유지는 기준 제어기와 함께 실행된다.

## PLACE가 배포 모델에 없는 정확한 이유

1. `policy_metadata.yaml`의 완료 stage가 PICK 계열 두 개뿐이다.
2. `runtime_manifest.yaml`이 `supported_commands: [PICK]`만 선언한다.
3. 공식 100회 평가는 `full_tower` PICK만 수행했다.
4. 실제 로봇 Python/C++ 런타임도 이 계약에 맞춰 PLACE를 거부한다.
5. 환경의 PLACE는 별도 에피소드로 시작하며, PICK 성공 뒤 같은 에피소드에서 PLACE까지 이어지는 성공 조건이 없었다.

과거 `arm_delivery_residual_v3_robot_stay`는 PICK/PLACE stage를 모두 이수해 `place_full_tower` 99%, `pick_place_mixed` 99%, `sim2real_robust` 95%를 기록했다. 그러나 이 모델은 pitch coupling 도입 전 action schema v2이므로 현재 실기 계약으로 그대로 되돌릴 수 없다.

2026-08-02에 현재 pitch-hold v3를 변경 전 체크포인트 그대로 재평가했다.

| 평가 | 결과 | 해석 |

| 강제 `pick_place_mixed`, 20회 | 100%, 충돌 0 | 독립 PICK/PLACE 에피소드 진단일 뿐 연속 배송 아님 |

## 새 전체 배송 계약

관측 33차원과 action 4차원은 유지해 실제 로봇 C++/Python 정책 actor와 호환되게 한다. 기존 네 phase도 그대로 사용한다.

```text
PICK_REACH
  → gripper close / object attached
PICK_TO_STAY
  → 파지 상태로 Stay 안정 판정
  → transport_hold_steps 동안 파지 유지
  → 외부 베이스가 배송 위치에 도착한 상태를 handoff로 반영
PLACE_REACH
  → 배송 위치의 ArUco/목표 좌표로 joint1 포함 재전개
  → release gate 연속 통과 후 gripper open
PLACE_TO_STAY
  → 물체 배치 오차와 빈 팔 Stay를 동시에 만족해야 성공
```

MuJoCo 팔 모델의 베이스는 고정되어 있으므로 바퀴 주행 자체를 PPO 팔 정책에 학습시키지 않는다. 실제 로봇에서도 베이스 이동은 이동 제어기가 담당하고, 팔 정책은 Stay 파지 유지와 도착 후 PLACE를 담당한다. 연속 배송 에피소드는 이 두 제어기 사이 handoff를 모델링한다.

## 새 성공 조건

한 에피소드의 성공은 다음을 모두 만족해야 한다.

1. 임의 위치·yaw의 물체를 파지한다.
2. 물체 최소 clearance를 지키며 실제 Stay로 돌아온다.
3. 지정 시간 동안 물체를 놓지 않고 Stay를 유지한다.
4. 출발 위치와 분리된 배치 목표로 다시 접근한다.
5. pitch, bearing, XYZ release gate를 연속 통과한 뒤 물체를 놓는다.
6. 배치 오차 `<= 15 mm`를 유지한다.
7. 빈 그리퍼로 실제 Stay에 복귀해 안정 판정을 채운다.
8. 전체 과정에서 충돌 종료가 없어야 한다.

## 재학습 순서

현재 pitch-hold v3에서 이어서 학습한다.

1. `place_center`
2. `place_return_center`
3. `place_full_tower`
4. `delivery_center`
5. `delivery_full_tower`
6. `delivery_sim2real_robust`

마지막 단계는 ArUco 위치/yaw 잡음과 dropout, 타워 위치·높이, 물체 크기, 관절 damping, actuator gain, friction, action delay를 함께 무작위화한다. 최종 artifact는 PICK과 PLACE 두 명령 및 연속 배송 학습 완료 여부를 metadata에 명시한다.

## 승인 기준

- `delivery_full_tower`: 성공률 95% 이상, 충돌 0%
- `delivery_sim2real_robust`: 성공률 90% 이상
- PICK/PLACE 개별 회귀: 각각 95% 이상
- MuJoCo 뷰어에서 PICK, Stay 파지 유지, PLACE, release, 빈 팔 Stay를 육안 확인
- Python/C++ actor 출력 parity 재검증 후에만 실제 로봇 배포 후보로 승격

이 기준은 시뮬레이션 배포 후보 기준이며 실제 로봇 자동 배송 승인 기준은 아니다.
